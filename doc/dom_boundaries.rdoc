= DOM boundaries

<tt>Swill::View</tt>, <tt>Swill::Controller</tt>, <tt>Swill::Ownership</tt>, <tt>Swill::Bindings</tt>,
<tt>Swill::Actions</tt>, <tt>Swill::Awakening</tt>, and <tt>Swill::Controller::List</tt> are
Ruby-authored framework classes compiled from Ruby that names DOM types. DOM traversal, control rendering,
event selection, action parsing, and listener ownership stay in those classes.
The handwritten runtime only resolves metadata-aware key paths and dispatches
generated method names.

Ownership follows a sparse view tree. An element becomes a <tt>View</tt> only when it
carries <tt>klass</tt>, <tt>controller</tt>, or <tt>outlet</tt>; elements with only <tt>bind</tt> or
<tt>data-action</tt> stay raw DOM, and templates and JSON scripts are inert content.
<tt>klass</tt> names a <tt>View</tt> subclass and may share an element with <tt>controller</tt>. A
controller's <tt>parent</tt> and <tt>child_controllers</tt> are derived from that tree.

Controllers declare <tt>outlet :name, type: ...</tt> and markup names the element with
<tt>outlet="name"</tt>. Outlets connect between <tt>view_did_load</tt> and bindings, only from
the controller's owned region including child-controller roots. The value is
the child controller, the element's view, an inert <tt><template></tt>, or JSON from a
<tt><script type="application/json"></tt> passed through <tt>decode_outlet_data</tt>. The
declared type names the value, <tt>T::Hash[String, String]</tt> for a JSON object or
<tt>Swill::View</tt> for an input, and a typed outlet's value is checked against it
at awakening. Undeclared, duplicate, unresolved required, and mistyped outlets
raise; <tt>optional: true</tt> outlets may be absent. Binding and action
scans stop at nested <tt>[controller]</tt> boundaries, so each element is wired by its
direct owner only. Awakening runs <tt>view_did_load</tt>, wiring, and <tt>awake_from_dom</tt>
for each controller children first, then <tt>controller_did_load</tt>, then the
appearance hooks. <tt>unload</tt> runs <tt>view_will_disappear</tt>, the controller's
bindings, everything it retained, its own observation state, its descendants,
and <tt>view_did_disappear</tt>, exactly once.

<tt>Swill::Application</tt> is the top of the responder chain for one launched region.
It records itself on its root element, so a root controller finds it by walking
up from its own element; <tt>application_did_launch</tt> and
<tt>application_will_terminate</tt> bracket its life. Actions resolve through the
responder chain: a controller handles an action when it has a matching
generated method, otherwise its parent tries, then the application, and an
action nobody handles raises. Actions default to <tt>click</tt>; <tt>event:action</tt>
selects another DOM event.

Bindings are Ruby key paths. <tt>bind="path"</tt> is two-way for form controls and
one-way for text; <tt>bind-prop="path"</tt> writes the DOM property named by the
HTML attribute one way, so <tt>bind-disabled</tt>, <tt>bind-hidden</tt>, and <tt>bind-readonly</tt>
set the matching properties with Ruby truthiness, and <tt>bind-data-*</tt> names go
through attributes because they are not properties. Paths resolve under the
controller's <tt>binding_root</tt>, a Symbol naming a property or nil for the
controller itself, and a leading <tt>@</tt> binds against the controller regardless
of the root. Reader chains may end in <tt>strip</tt>, <tt>upcase</tt>,
<tt>downcase</tt>, <tt>blank?</tt>, <tt>present?</tt>, <tt>empty?</tt>, or <tt>nil?</tt>; the first three
predicates answer for a nil intermediate, and any other reader on nil yields
nil. A segment that reaches a Hash reads its key, nil when absent, as
key-value coding does for a dictionary, and a writable control sets an
existing key; hash entries are not observable, so replace the hash to notify.
A write through a missing owner is dropped; a read-only leaf on a writable
control fails at wiring.

A <tt>bind</tt> on a child controller's root belongs to the parent and assigns the
child's <tt>represented_object</tt>, nil included; it is wired when the parent loads,
so a fragment awakened later must be present under its parent before the
parent awakens or be bound by the parent explicitly. <tt>bind-*</tt> on that root
belongs to the child. <tt>bind(:target, to: source, key_path: "a.b")</tt> keeps a declared
property equal to a path on another object until <tt>unbind</tt>, <tt>unbind_all</tt>, or
<tt>unload</tt>; <tt>null_placeholder:</tt> is what the target receives when the path has no
value, so a path through a nilable object can feed a property that is not one.
<tt>observe(name, callback)</tt> observes the receiver's own property and
<tt>observe(object, name, callback)</tt> another object's; either way the receiver is
the observer, so either way it retains the observation and lets it go at
<tt>unload</tt>. For one of its own properties a <tt>name_did_change</tt> hook needs no
observation at all. <tt>retain(disposer)</tt> claims any other disposer the same way,
as Cocoa's retain claims an object, <tt>release(disposer)</tt> gives one up before
then, and <tt>observe_notification</tt> is a retain over
<tt>NotificationCenter.default.add_observer</tt>. An object ends by itself with
<tt>dealloc</tt>, which releases everything it retained and then leaves the
observation graph; <tt>disconnect</tt> leaves the graph without ending, keeping stored
values so computed properties resubscribe on the next read.

The application owns the first responder. <tt>make_first_responder</tt> follows
Cocoa: a responder must accept, the current one may refuse to resign, and a
refusal to become leaves the application holding it. Views accept and focus
their first focusable element; controllers accept when their view has one. A
<tt>focusin</tt> on the root reconciles the first responder after the browser moves
focus, restoring focus when the holder refuses. Focus leaving for the
browser's own chrome or dead space keeps the first responder, as Cocoa does,
so keys still reach it when focus returns; focus moving to another part of
the page outside the application releases it. <tt>keydown</tt> and <tt>keyup</tt> go to the
first responder: Escape, Enter, and Tab become <tt>cancel_operation</tt>,
<tt>insert_newline</tt>, and <tt>complete</tt>, and unhandled keys and those methods continue
up the responder chain to the application. Tearing down a region releases a
first responder inside it.

Windows are template-backed. <tt><template for="window" name="x"></tt> anywhere, or
<tt><template name="x"></tt> directly under the application root, is inert content.
A <tt>[window="main"]</tt> container is filled at launch from the template its
<tt>name</tt> attribute selects, or keeps and captures its pre-rendered content.
<tt>load_window_content("main", "x")</tt> tears down the old content, clones and
awakens the new, and hands the first responder to its top controller.
<tt>show_window("x")</tt> clones a template into the root as a window, or into a
chosen element with <tt>show_window("x", into: element)</tt>, showing a <tt><dialog></tt>
root, and returns a
<tt>Swill::Window</tt> whose <tt>closed</tt> promise resolves
when <tt>dismiss(controller)</tt> tears it down and restores the saved first
responder. Code-created content awakens through a <tt>MutationObserver</tt> on the
root, and removed content is torn down, so markup and code share one
activation path; <tt>Awakening#detach</tt> does the same explicitly.

Restoration reuses the binding machinery. A window controller declares
<tt>restorable :query, key: :q</tt> or `restorable "people.selected_id",
key: :selected`; the path is a bindable path whose first segment must be a
declared property, and the compiler records the leaf's declared type so
integers and booleans decode from the fragment while everything else stays a
string. The URL fragment holds <tt>main=content</tt> for a container's content and
<tt>main.q=value</tt> for its controller's state. At launch the fragment chooses a
container's content and its values are written through the same path writer
bindings use, then <tt>controller_did_restore(restored)</tt> runs before
<tt>controller_did_load</tt>. Changes to restorable paths replace their fragment
values; <tt>load_window_content</tt> pushes a history entry; Back/Forward reloads
the content the fragment names without writing history. Unknown content and
values of the wrong type are reported and ignored, since the URL is untrusted.

<tt>Swill::Controller::List</tt> is the NSTableView analog. It clones one row per
arranged object from its own <tt><template for="row"></tt> into its <tt>rows</tt> outlet, or
its root without one, and wires each row's <tt>bind</tt> and <tt>bind-*</tt> attributes
against that object and its <tt>data-action</tt> attributes against the list, so a
row's button reaches the list first and then the responder chain, and
<tt>row_for(sender)</tt> tells a handler which row the sender sits in. Rows are views
owned by the list; a <tt>controller</tt> inside a row awakens under the list, and
<tt>bind="@"</tt> on its root hands it the row's object. The collection is
<tt>represented_object</tt>, usually fed by the parent's <tt>bind</tt> on the list root; a
new collection re-renders, and pre-rendered rows are replaced at awakening.
Selection is by identity: <tt>selected_objects</tt> is stored, <tt>selected_indexes</tt> and
<tt>selected_object</tt> derive from it, and <tt>selected_object_id</tt> follows the leading
object's model id and can be written to select by id now or once the object
arrives, which is what <tt>restorable :selected_object_id</tt> keeps in the fragment.
A click selects, shift-click extends when <tt>allows_multiple_selection</tt> or the
<tt>multiple</tt> attribute is on, arrow keys move the selection of a first-responder
list, and Enter or a double-click sends <tt>activate_selection</tt> up the responder
chain with the list as sender, quietly when nobody handles it.
<tt>selected_object_did_change(previous, object)</tt> runs when the leading object
changes.

<tt>Swill::Controller::SortableList</tt> orders the rows by one column. <tt>sort_key</tt>
and <tt>sort_direction</tt> (<tt>ascending</tt> or <tt>descending</tt>) are stored properties, so
they bind and can be <tt>restorable</tt>; a header cell with `data-column="name"
data-action="sort_by"<tt> toggles that column, and </tt>sort_states` maps the sorted
column to its direction for <tt>bind-aria-sort="sort_states.name"</tt>. Values
compare with nil last, numbers and booleans by value, and everything else as
text, and the selection follows its objects through a reorder.

<tt>Swill::Controller::EditableList</tt> edits rows in place. Enter or a double-click
on a row, or <tt>begin_editing(index)</tt>, clones the list's own
<tt><template for="editor"></tt>, whose root is a <tt>controller="Swill::Controller::InlineEditor"</tt>,
after the row and gives it the keyboard. The edit works on a copy, a model's
<tt>draft</tt> or a duplicate of a plain object, held as the list's <tt>edited_object</tt>
and the editor's <tt>represented_object</tt>, so the editor's bindings write into
the copy. Enter commits: a model takes the draft back with <tt>apply_draft</tt> and
stays the row's object, a plain object is replaced in the collection; Escape
discards. Focus leaving the editor asks <tt>editor_should_end_editing</tt>, which
discards an unchanged copy and otherwise commits when <tt>confirm_edit?</tt> agrees,
or refuses and keeps focus. <tt>validation_error</tt>, <tt>editing_did_fail_validation</tt>,
and <tt>edited_object_has_changes?</tt> are the other hooks; sorting commits an edit
in progress first, and a new collection discards it.
<tt>Swill::Control</tt> is the NSControl analog: a view over a form element whose
<tt>delegate</tt> may refuse <tt>control_should_resign_first_responder(control, next)</tt>,
so an inline editor holds focus in a control until the edit is accepted; the
editable list makes its editor the delegate of every control inside it.
<tt>Swill::Control::TextField</tt> (<tt>klass="Swill::Control::TextField"</tt> on an input
or an element containing one) keeps a <tt>value</tt> property equal to the input
both ways, and <tt>Swill::Control::Select</tt> keeps <tt>options</tt> and <tt>value</tt> for a
native select, leaving markup options in place as a prefix.
<tt>Swill::Control::CustomSelect</tt> is a stylable select built inside a plain
element: a button showing the chosen option and a listbox of hashes with
<tt>"value"</tt>, <tt>"label"</tt>, and optional <tt>"description"</tt> and <tt>"icon"</tt>. Enter and
Space toggle it, arrows move, Escape and outside pointers close it, and a
choice dispatches <tt>input</tt> and <tt>change</tt> on the element as a native select
would.

A <tt>bind</tt> on an element whose <tt>klass</tt> is a control keeps the control's <tt>value</tt>
property equal to the path both ways, so `<div klass="Swill::Control::CustomSelect"
bind="choice"><tt> edits </tt>choice` and follows it.

<tt>Swill::NotificationCenter.default</tt> is the NSNotificationCenter analog:
<tt>post(name, object, user_info)</tt> and <tt>add_observer(name, callback)</tt>, which
returns the callable that ends the observation, named as Cocoa names it because
observing a notification is not observing a property; a controller's
<tt>observe_notification</tt> retains that callable, so the observation ends at
<tt>unload</tt>. The application posts <tt>first_responder_did_change</tt>
with the new responder as user info. <tt>Swill::Runtime.nameOf(object)</tt> gives an
object's installed class name.

<tt>Swill::Controller::Editor</tt> is the base: <tt>binding_root</tt> is <tt>represented_object</tt>,
with NSEditor's <tt>commit_editing</tt>, which returns whether pending edits could be
pushed into the object, and <tt>discard_editing</tt>, on Enter and Escape. The host
holds the object already, so nothing is returned; an editor that answers
false keeps the edit open.
