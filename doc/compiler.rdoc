= Compiler and Runtime

This document describes how Swill's Ruby2JS build turns Ruby source into
browser JavaScript, which Ruby forms it accepts, how it lowers them, and what
the handwritten runtime provides. It is the reference for the supported
boundary. The README covers commands and layout; <tt>PLAN.md</tt> at the repository
root covers goals and roadmap.

Source of truth: <tt>rb/compiler/</tt> and <tt>rb/runtime/</tt>. When this
document and the code disagree, fix one of them in the same change.

== Pipeline

  Ruby source
    → Ruby2JS.parse                 (Prism walker on Ruby 3.4+, parser gem otherwise)
    → Loader#evaluate               (class bodies run in a container; method bodies never do)
    → Knowledge#collect             (structure from the AST, declarations by reflection)
    → Compiler#validate!            (ordering, ancestry, member collisions)
    → Ruby2JS.convert per entry     (Swill filters + Return; Pragma on shared Ruby)
    → esbuild --loader=js           (formatting only; part of every emission)
    → *.classes.mjs / *.meta.mjs / *.mjs
    → esbuild --bundle              (readable and minified IIFEs with source maps)

Two compiler instances run per build. The framework instance compiles
<tt>rb/framework/</tt>. Its <tt>knowledge.interface</tt> is handed in memory to the application
instance, which compiles <tt>examples/</tt> against those facts and imports the
framework's identifiers from the published <tt>Swill</tt> global rather than
recompiling them.

Both Ruby2JS parsers are supported. Only expression ranges are read from
location objects, because the two parsers disagree on token-level locations.
The suite passes and produces identical bundles under either.

== Knowledge collection

Only one thing about a Ruby class body genuinely cannot be ported to the
browser 1:1: it runs at class-definition time, and the browser must receive
classes whose accessors and metadata are already installed. So the compiler
runs it. <tt>Swill::Ruby2JS::Loader</tt> evaluates every source on MRI inside an
anonymous container module, and <tt>Swill::Ruby2JS::Knowledge</tt> then builds one
entry per class or mixin from two sources: the AST, for everything only the
source knows, and the defined class, for everything the class body declared.
Method bodies never run; the sources only have to load.

Collection is three passes per file. First the constants the source would
declare, so a file that would reopen a class the compiler already knows is
rejected before it can mutate the shared framework container. Then the
evaluation. Then the entries.

An entry holds:

<tt>name</tt>, <tt>identifier</tt> :: Ruby constant path and its JavaScript identifier — from AST
<tt>kind</tt> :: <tt>class</tt> or <tt>mixin</tt> — from AST
<tt>scope</tt>, <tt>parent</tt> :: Enclosing namespaces and the superclass constant as written — from AST
<tt>includes</tt> :: Mixins in factory-nesting order (see {Mixins}[#mixins]) — from AST
<tt>methods</tt> :: Name, JavaScript member name, arity, signature parameter types, signature return type, and whether it is asynchronous — from AST, plus <tt>forward</tt>
<tt>class_methods</tt> :: A mixin's <tt>ClassMethods</tt> bodies, compiled as written — from AST
<tt>properties</tt> :: One descriptor per <tt>property</tt>, in declaration order, however it was declared — from class
<tt>registries</tt>, <tt>settings</tt> :: What a mixin's <tt>ClassMethods</tt> declares — from class
<tt>registry_values</tt>, <tt>setting_values</tt> :: The class's exact registry snapshots, and what it set a setting to — from class
<tt>restorations</tt> :: Bindable paths kept in the URL fragment — from class
<tt>included_properties</tt> :: What a mixin's <tt>self.included</tt> hook declares, read from a class that includes it — from class

Imported entries from another compiler carry the same fields, minus the AST.

=== Containers

A container is an anonymous <tt>Module</tt> with a temporary name, so a build adds
nothing to the global namespace and is collectable when it ends. Inside one,
<tt>require</tt> and <tt>require_relative</tt> are inert: the build decides the order and
hands the sources over in it.

The framework's container is built once per process. Each application's
container is given the framework's own constants, so an application resolves
<tt>Swill::Controller</tt> and subclasses the same class object. An application may
not declare anything below an imported root such as <tt>Swill</tt>; its declarations
remain in its own namespaces. A watch rebuild evaluates only the application's
files.

Before Ruby evaluates a source, the collector checks its class and module
bodies against the declaration vocabulary known for the whole source. Loading
is transactional: evaluation and collection either both finish, or newly
defined constants, entries, and blocks are restored. Corrected source at the
same path can therefore be tried again after a failed build. Application and
plugin source is trusted Ruby; the preflight exists to make compiler behavior
deterministic, not as a security boundary.

Sigs and declarations may name a DOM class, so a stub for every entry in
<tt>knowledge/dom.rb</tt> is defined in the container first, parents before children.

A load error becomes a <tt>CompileError</tt> reading <tt>path:line: message</tt>, with the
container's prefix stripped, and Sorbet's declaration state is reset so a
failed class body cannot poison the next one.

=== Modules

A <tt>module</tt> is a mixin, a namespace, or both. Nested classes and non-
<tt>ClassMethods</tt> modules are collected as their own entries under the module's
name. The module is also collected as a mixin when it is empty or has any
non-namespace body. Namespaces are not entries.

=== Class bodies

A class or mixin body may contain only:

<tt>def name(positional, args)</tt> :: Collected as a method. Names match <tt>/\A[a-z_]\w*[!?=]?\z/</tt>; <tt>method_missing</tt> is rejected; <tt>initialize</tt> compiles to <tt>constructor</tt>. Arguments are positional; optional ones are contiguous and compile per {Optional positional arguments}[#optional-positional-arguments]
<tt>sig { ... }</tt> :: Parameter and return types are recorded for lowering, then erased
<tt>extend T::Sig</tt> :: Erased
<tt>include A, B</tt> / <tt>include A</tt> :: Recorded; targets must be previously defined mixins
<tt>property :name, ...</tt>, or any declaration macro :: Ran when the class body ran; the entry reads what it declared off the class (see {Declaration macros}[#declaration-macros])
<tt>def self.name(positional, args)</tt> :: Classes only: a static method under the same name rules. Inside it <tt>self</tt> is the class and a bare <tt>new</tt> constructs it; <tt>self.new</tt> is rejected as a name
<tt>async def name(...)</tt>, <tt>async def self.name(...)</tt> :: The same, marked asynchronous: it compiles to an <tt>async</tt> method and its body may <tt>await</tt>
<tt>def self.included(base)</tt> :: Mixins only; see {Included hooks}[#included-hooks]
<tt>module ClassMethods</tt> :: Mixins only; see {Class methods}[#class-methods]
nested <tt>class</tt> / <tt>module</tt> :: Mixins only; collected as namespaced entries

Anything else is a compile error naming the statement.

=== Declaration macros

A declaration is ordinary Ruby: a class method that runs when the class body
runs. <tt>property</tt> is the primitive every other declaration is built on, and a
macro is a class method marked with <tt>macro</tt>, which makes it callable in a class
body and keeps it out of the emitted JavaScript.

  module Swill
    module Model
      module Relationships
        module ClassMethods
          extend Swill::Declarations

          inheritable_registry :model_relationships

          macro def has_many(name, type:, key: name, url: nil, will_access: true)
            declare_relationship(name, type, key, url, "many", will_access)
          end
        end
      end
    end
  end

A macro may declare five kinds of thing, all of them serializable:

<tt>property</tt> (and <tt>outlet</tt>, <tt>restorable</tt>, <tt>attribute</tt>, <tt>has_many</tt> built on it) :: A descriptor the runtime installs as a prototype accessor
<tt>inheritable_registry</tt> entries :: Data in the class's own registry
<tt>class_setting</tt> values :: A value applied at installation
<tt>forward</tt> :: A real, typed method on the class
<tt>will_access:</tt> on a property :: The read notifies the object, so a value can load itself

Nothing else reaches the browser: no macro machinery is emitted, and a plugin's
macro emits the same shapes with no change to the compiler. A macro may not
<tt>define_method</tt> with a block, because the block closes over the macro's locals
and compiling it would mean substituting captured values into an AST.

  property :loud, type: T::Boolean, default: false
  attribute :name, type: String, default: "", key: :display_name

  property :label, type: String do
    loud ? name.upcase : name
  end

  outlet :name_field, type: Swill::View
  outlet :seed, type: T::Hash[String, String]
  outlet :extra, type: T.untyped, optional: true

Name :: Matches <tt>/\A[a-z_]\w*\??\z/</tt>; a <tt>?</tt> suffix only on computed properties
<tt>type:</tt> :: A Sorbet type, or its text when the class it names is defined later
<tt>default:</tt> :: Literal string, number, symbol, <tt>nil</tt>, <tt>true</tt>, <tt>false</tt>, or an empty <tt>[]</tt> or <tt>{}</tt>; the emitted default is a function, so each instance gets its own collection. Anything mutable is rejected
Block :: A computed property: no block arguments, no <tt>default:</tt>
<tt>attribute:</tt>, <tt>key:</tt> :: Marks the property an attribute with a wire key, which is what the validation, dirty-tracking, and codec paths read
<tt>outlet:</tt>, <tt>optional:</tt> :: Marks the property an outlet, connected at awakening
<tt>will_access:</tt> :: The getter calls <tt>property_will_access(name)</tt> before it resolves

The framework's own macros:

<tt>attribute :name, type:, default:, key:</tt> :: A property marked as an attribute, and the same declaration as data in <tt>model_attributes</tt>
<tt>outlet :field, type:, optional:</tt> :: A stored, nilable, observable property with <tt>outlet</tt> and <tt>optional</tt> metadata. Declared on <tt>Swill::Controller</tt>, so only a controller can call it. The type names the connected value: a framework class for a view or child controller, <tt>T::Hash[...]</tt> or <tt>T::Array[...]</tt> for decoded JSON, <tt>T.untyped</tt> for anything. Awakening checks a typed outlet's value against the type shallowly, as <tt>T.cast</tt> does, so a JSON script that decodes to the wrong shape fails by outlet name
<tt>restorable :path, key: :k</tt> :: A dotted property path the application keeps in the URL fragment. The leaf's declared type is recorded when every segment is statically typed. Declared on <tt>Swill::Controller</tt>
<tt>has_many :name, type:, key:, url:, will_access:</tt> :: The value property (<tt>T::Array[Type]</tt>, defaulting to <tt>[]</tt>), its key-value loading state as three more properties (<tt>name_loading</tt>, <tt>name_loaded</tt>, <tt>name_error</tt>), a <tt>model_relationships</tt> entry, and <tt>load_name</tt> / <tt>reload_name</tt> as real typed methods. <tt>:id</tt> in <tt>url:</tt> stands for the owner's id
<tt>has_one :name, ...</tt> :: The same, with <tt>T.nilable(Type)</tt> defaulting to <tt>nil</tt>

A relationship, or an outlet, may name a class defined later by writing its
name as a string, which is what a genuine cycle needs; the descriptor carries
the installed name either way, and the compiler checks that the name is a
class once the whole graph is known.

=== Class settings

  class Menu < Swill::Model::Base
    endpoint "/api/menus"
    resource_type "menus"
    codec Swill::Model::PlainJSON      # JSON:API unless declared
  end

A class body may set any <tt>class_setting</tt> an included <tt>ClassMethods</tt>, or an
ancestor's, declares. The value is emitted as <tt>settings</tt> in the meta object and
applied through the setting method at installation, and is stored under the
Ruby name so <tt>Runtime.classWithSetting</tt> can look a class up by it. Reading a
setting in a class body says nothing and is rejected; a name nothing declares
is rejected as an unsupported class-body statement, with the file and line it
was written on.

=== Included hooks

A mixin may declare exactly one <tt>def self.included(base)</tt> whose body consists
only of <tt>base.extend(ClassMethods)</tt> and declarations on <tt>base</tt>. Every class
that includes the mixin runs the hook and so owns its own descriptors, and a
computed block compiles in each receiving class. The hook is never emitted, and
the compiler runs it once more against a throwaway class so the mixin's own
RBI can name what it declares.

=== Class methods

A mixin's <tt>module ClassMethods</tt> may contain:

<tt>extend Swill::Declarations</tt> :: Accepted and erased: the browser gets the declarations' result, not the primitives
<tt>inheritable_registry :name</tt> / <tt>:name, :array</tt> :: A per-class registry that copies its parent's contents on first access. Its exact declaration-time contents travel in the meta object as <tt>registries</tt> and replace the runtime copy at installation
<tt>class_setting :name</tt> :: A per-class value that falls back to the parent's; a class body sets it with a literal (see {Class settings}[#class-settings]), and the value is stored under the Ruby name so <tt>Runtime.classWithSetting</tt> can look a class up by it
<tt>def name(positional)</tt> :: Compiled as a class-side method; inside it <tt>self</tt> is the class, so bare calls reach static methods, other <tt>ClassMethods</tt> methods, registries, and settings
<tt>macro def name(...)</tt> :: A declaration macro. It runs when a class body calls it and is never emitted, so its body may use the full declaration vocabulary
<tt>extend T::Sig</tt>, <tt>sig { ... }</tt> :: Read for parameter and return types, never emitted

=== Optional positional arguments

JavaScript has no leading optional parameter — <tt>function m(a = null, b, c)</tt>
binds left to right, so a two-argument call fills <tt>a</tt> and <tt>b</tt> rather than <tt>b</tt>
and <tt>c</tt>. Rather than reshape the Ruby around that, a method with optional
arguments compiles the way Cocoa spells an overload: **one method per arity,
named for the optionals it takes.**

  sig { params(greeting: String, name: String).returns(String) }
  def greet(greeting = "Hello", name)
    "#{greeting}, #{name}"
  end

  greetWithGreeting(greeting, name) { return `${greeting}, ${name}`; }
  greet(name) { return this.greetWithGreeting("Hello", name); }

Naming :: The variant taking no optionals keeps the plain name. Each wider one is <tt>name_with_</tt> followed by the optionals it takes, joined by <tt>_and_</tt>: <tt>greet</tt> / <tt>greet_with_greeting</tt>; <tt>span</tt> / <tt>span_with_b</tt> / <tt>span_with_b_and_c</tt>
Body :: The widest variant carries the body. Every shorter one hands it the defaults in the positions Ruby's own binding would fill: required arguments first, optionals absorbing what is left
Metadata :: Each variant is its own entry with a fixed arity; the wider ones carry <tt>family</tt>, which is how <tt>Runtime.invoke</tt>, <tt>read</tt>, and <tt>performAction</tt> resolve a name and an argument count to one method
Call sites :: A send to a typed receiver emits the variant whose arity is the argument count, and the signature's parameter types follow the parameters, so a lambda passed to a shorter variant is still typed
<tt>super</tt> :: Reaches the parent's variant of the same width, so an override keeps its own defaults
Rejected :: Keyword, splat, and block parameters; non-contiguous optionals; a predicate, bang, or writer with an optional; optionals on a static or <tt>ClassMethods</tt> method; a block with an optional, since whatever yields to it calls at a fixed arity; an override whose accepted arities differ from the inherited family, which would shadow only part of it; and a statically resolved call with no matching arity. A signature must name the method's parameters in the same order

=== Pragmas

Comments of the form <tt># Pragma: array</tt>, <tt># Pragma: hash</tt>, and
<tt># Pragma: string</tt> are passed to Ruby2JS's Pragma filter as type hints on the
shared surface. Any other pragma name is rejected, because control pragmas
such as <tt>skip</tt> or <tt>extend</tt> would desynchronize collected metadata.

== Generated output

=== Identifiers

<tt>Person</tt> → <tt>Person</tt> :: Plain names are unchanged
<tt>Demo::Person</tt> → <tt>Demo__Person</tt> :: <tt>::</tt> becomes <tt>__</tt>
<tt>Demo_Thing</tt> → <tt>Demo_uThing</tt> :: Source <tt>_</tt> becomes <tt>_u</tt> first, so <tt>A::B</tt> and <tt>A__B</tt> stay distinct
<tt>Runtime</tt>, <tt>Superclass</tt>, <tt>Object</tt>, <tt>Array</tt>, <tt>String</tt>, <tt>Number</tt>, <tt>Math</tt>, <tt>JSON</tt>, <tt>Error</tt>, <tt>Promise</tt>, <tt>MutationObserver</tt>, <tt>URLSearchParams</tt> → <tt>Ruby_Runtime</tt> and so on :: Reserved plumbing and JavaScript intrinsics
<tt>row_elements</tt>, <tt>awake_from_dom</tt> → <tt>rowElements</tt>, <tt>awakeFromDOM</tt> :: Members are camelCase; <tt>DOM</tt>, <tt>URL</tt>, <tt>JSON</tt>, and <tt>HTML</tt> stay upper-case
<tt>row_element?</tt>, <tt>dirty?</tt> → <tt>isRowElement</tt>, <tt>isDirty</tt> :: A predicate gains <tt>is</tt>
<tt>accepts_first_responder?</tt>, <tt>rows_are_views?</tt>, <tt>confirm_edit?</tt> → <tt>acceptsFirstResponder</tt>, <tt>rowsAreViews</tt>, <tt>confirmEdit</tt> :: A predicate phrased as a verb (first word in the compiler's verb list, or <tt>are</tt>, <tt>is</tt>, <tt>has</tt> inside) keeps its phrasing
<tt>mark_clean!</tt> → <tt>markClean</tt> :: The bang is dropped; a class defining both <tt>x</tt> and <tt>x!</tt> is rejected as a member collision
<tt>__swill_view__</tt> → <tt>__swill_view__</tt> :: A leading underscore marks a JavaScript expando, left as written

<tt>Swill::Runtime</tt> in source always refers to the handwritten runtime.

=== Classes and mixins

A class compiles to <tt>class Demo__Person extends Swill__Model__Base { ... }</tt>
containing only its methods. Properties are not on the class; the runtime
installs accessors from metadata. Instance variables compile to underscored
fields (<tt>@view</tt> becomes <tt>this._view</tt>).

A mixin compiles to a subclass-layer factory:

  function StripName(Superclass) {
    class StripName_Layer extends Superclass {
      normalize(value) { return Runtime.strip(super.normalize(value)); }
    }
    return StripName_Layer;
  }

At install time the runtime inserts the layers between the class and its
parent, so native <tt>super</tt> works and no method is copied.

<tt>include A, B</tt> places <tt>A</tt> before <tt>B</tt> in Ruby lookup; two separate <tt>include</tt>
statements place the later one first. <tt>entry["includes"]</tt> stores factory
nesting order, which is the reverse of lookup order, and both forms are tested
against MRI.

A <tt>ClassMethods</tt> module compiles to a second factory,
<tt>Feature_ClassMethods(Superclass)</tt>, that returns a prototype object. The
runtime copies its own property descriptors onto the receiving constructor
instead of splicing it into the constructor chain, because a JavaScript
subclass uses that chain as its <tt>super()</tt> target.

=== The meta object

  export const meta = {
    mixins: {
      "StripName": {factory: StripName, methods: {"normalize": {"arity": 1}}},
      "Swill::Model::Attributes": {factory: ..., classFactory: ..., methods: {...}}
    },
    classes: {
      "Demo::Person": {
        constructor: Demo__Person,
        mixins: [NormalizeName, StripName, DecorateName],
        properties: {
          "name": {type: "String", attribute: true, key: "name",
                   defaultValue() { return ""; }},
          "label": {type: "String", attribute: false,
                    compute: function computeLabel() { return this.loud ? Runtime.upcase(this.name) : this.name; }},
          "blank?": {js: "isBlank", type: "T::Boolean", attribute: false, compute: ...},
          "badge": {type: "T.nilable(Demo::Badge)", attribute: false, outlet: true, optional: false,
                    defaultValue() { return null; }},
          "books": {type: "T::Array[Demo::Book]", attribute: false, willAccess: true,
                    defaultValue() { return []; }}
        },
        registries: {
          modelAttributes: {"name": {"name": "name", "key": "name", "type": "String", "default": ""}},
          modelRelationships: {"books": {"name": "books", "key": "books", "kind": "many",
                                         "type": "Demo::Book", "url": "/api/authors/:id/books"}}
        },
        methods: {"greeting": {"arity": 0}, "loadBooks": {"arity": 0}}
      }
    }
  };

<tt>meta</tt> is the serialization of each class's declaration-time state, and
<tt>Runtime.install</tt> is its deserializer. Registry values and settings are plain
data the runtime applies without knowing what any of it means; a plugin's macro
emits the same shapes. <tt>meta</tt> contains no Ruby source and no compiler AST. Object keys use the Ruby name; <tt>js</tt> is present only
when the JavaScript member differs. A <tt>__proto__</tt> key is emitted as a computed
key so it stays an ordinary entry.

=== Modules and publishing

<tt>Compiler#modules(name:, runtime:, framework:, publish:, launch:)</tt> emits three
files:

<tt>name.classes.mjs</tt> :: Imports plus class and factory definitions; inert
<tt>name.meta.mjs</tt> :: Imports the definitions and exports <tt>meta</tt>
<tt>name.mjs</tt> :: <tt>Runtime.install(meta)</tt>; with <tt>publish:</tt>, also freezes the global

The generic compiler can publish and launch directly with these options. The
Swill distribution instead compiles the framework without them and bundles a
small handwritten browser entrypoint. That entrypoint installs the framework,
passes its definitions to <tt>browserAPI</tt>, freezes the returned <tt>Swill</tt> global,
and installs <tt>Swill::Launcher</tt>. The browser API retains the definitions for
compiled bundles and adds friendly class names, JavaScript registration, and
manual startup. <tt>Swill::Launcher</tt> starts an application declared by
<tt>[application]</tt>; <tt>Swill.start()</tt> starts a JavaScript application explicitly.
The application build imports every framework identifier from that global
through a generated shim, so the application bundle contains neither the
runtime nor the framework classes. Only <tt>Swill</tt> is global.

<tt>Swill.register</tt> converts <tt>static properties</tt>, <tt>static outlets</tt>, explicit
actions, and native getters into the same <tt>meta.classes</tt> descriptors emitted
by the compiler. An outlet descriptor takes <tt>optional</tt>; its value is untyped. It then delegates to <tt>Runtime.install</tt>; JavaScript classes do
not have a separate observation or dispatch path.

=== Sorbet artifacts

<tt>Compiler#rbi</tt> :: Typed readers and writers for every declared property, plus <tt>ClassMethods</tt> registries and settings
<tt>Compiler#type_probes</tt> :: One typed method per declaration whose body is the default or computed expression, so Sorbet checks it against the declared type

Both are regenerated by <tt>rake build</tt> into <tt>sorbet/rbi/generated.rbi</tt> and
<tt>sorbet/checks/declarations.rb</tt>. Neither is executed or shipped.

== Native types

One filter chain compiles every entry: <tt>RubySurface</tt>, then <tt>Return</tt> for
implicit returns, then <tt>RubyCalls</tt>, which turns any remaining send into an
explicit call. What decides between Ruby semantics and JavaScript's is the
static type of the receiver, never the file.

The browser is described to the compiler once, in
<tt>rb/compiler/knowledge/dom.rb</tt>: the DOM classes and JavaScript intrinsics
framework code may name (<tt>Element</tt>, <tt>Node</tt>, <tt>Document</tt>, <tt>DOMWindow</tt>, <tt>Event</tt>,
<tt>KeyboardEvent</tt>, <tt>MouseEvent</tt>, <tt>HTMLTemplateElement</tt>, <tt>DocumentFragment</tt>,
<tt>HTMLCollection</tt>, <tt>NodeList</tt>, <tt>DOMTokenList</tt>, <tt>Selection</tt>, <tt>Location</tt>,
<tt>History</tt>, <tt>MutationObserver</tt>, <tt>MutationRecord</tt>, <tt>Promise</tt>, <tt>URLSearchParams</tt>)
with the members the framework uses, each marked as an attribute, an accessor,
or a method, with its type and parameters. The build writes that table out as
<tt>sorbet/rbi/dom.rbi</tt>, so framework signatures say <tt>Element</tt> where a DOM value
is meant and Sorbet checks the calls; the compiler reads the same table to
lower them. <tt>DOMWindow</tt> is the browser's window, since <tt>Swill::Window</tt> is the
framework's own class.

A DOM class, nilable or not :: A listed attribute or accessor is property access, a listed method is a call, whatever the source's parentheses; <tt>name = value</tt> is an assignment. An unlisted member follows the source: parentheses or arguments call, none reads. <tt>?.</tt> is JavaScript's own and keeps the source's parentheses. Operators and indexing stay with the converter
The result of a native member :: The member's declared type when listed (<tt>getAttribute</tt> yields <tt>T.nilable(String)</tt>, so <tt>strip</tt> is Ruby's), the indexed element type for <tt>[]</tt> on a collection, <tt>T.self_type</tt> for <tt>cloneNode</tt>, otherwise an untyped JavaScript value on which every member is native
A DOM class constant :: <tt>new</tt> constructs it (<tt>MutationObserver.new(...)</tt>); a JavaScript intrinsic such as <tt>JSON</tt> passes through by name. A source constant of the same name wins and is encoded (<tt>Ruby_JSON</tt>) so it cannot shadow the global
A lambda or block passed to a native member :: Its parameters take the types the table declares for that callback (<tt>addEventListener</tt>'s listener receives an <tt>Event</tt>, <tt>NodeList#forEach</tt> an <tt>Element</tt>, the <tt>MutationObserver</tt> constructor its records), and locals assigned from them are typed in the body

DOM-typed values have JavaScript truthiness and identity equality, and a
block on one is a JavaScript callback. A <tt>T.let</tt> or <tt>T.cast</tt> to a DOM type, or
to <tt>T.untyped</tt>, is an annotation for Sorbet and the typer with no runtime
check: the browser's classes are not the runtime's to verify. <tt>T.untyped</tt>
means a Ruby object dispatched by name at run time, so a DOM value must be
typed as one; passing it through <tt>T.untyped</tt> would fail at first use.

<tt>Runtime</tt>, bare or as <tt>Swill::Runtime</tt>, names the handwritten runtime when no
source constant of that name is in scope.

== Lowering rules

These apply to the shared Ruby surface. Every rule is chosen from static facts;
the runtime is reached only where a fact is genuinely unavailable.

=== Static types

String, integer, boolean, <tt>nil</tt>, symbol, array, hash literals :: <tt>String</tt>, <tt>Integer</tt>, <tt>T::Boolean</tt>, <tt>NilClass</tt>, <tt>Symbol</tt>, <tt>Array</tt>, <tt>Hash</tt>
Interpolated string :: <tt>String</tt>
<tt>==</tt>, <tt>!=</tt>, <tt>!</tt> :: <tt>T::Boolean</tt>
Parameter :: Its <tt>sig</tt> parameter type
Local variable :: Inferred when its assignments' types merge (the same class or core type, nilable when any is nil, an empty <tt>[]</tt> or <tt>{}</tt> fitting a typed collection) and its first assignment is a statement, in the body or in a branch, loop, or block, that precedes every read; an assignment may refer to the variable itself; an assigned parameter loses its signature type
Instance variable :: <tt>T.nilable(Class)</tt> when every assignment anywhere in the class has a static type and the non-nil ones name one framework class; otherwise none. Inferred from the class's own AST, so a computed property's block, which is converted on its own, types its instance variables the same way a method does
<tt>left || right</tt> :: The right's type when both sides name the same class, nilable or not on the left: a nil left yields the right
<tt>Const.member(...)</tt> :: The <tt>sig</tt> return type of the static method, or of the method, registry, or setting an included <tt>ClassMethods</tt> provides; registries and settings are <tt>T.untyped</tt>. <tt>T.attached_class</tt> and <tt>T.self_type</tt> in the type stand for the receiving class
<tt>self.class</tt>, <tt>receiver.class</tt> for a framework-class receiver, <tt>self</tt> in a class method :: <tt>T.class_of(Class)</tt>
<tt>receiver.member(...)</tt> where the receiver is <tt>T.class_of(Class)</tt> :: As <tt>Const.member</tt>, and <tt>receiver.new</tt> yields the class
<tt>name(...)</tt> for an async method, without <tt>await</tt> :: <tt>Promise</tt>
<tt>await expression</tt> :: An async member's declared type (its signature names the value it yields); the element of a <tt>Promise[X]</tt> type from the DOM table; otherwise the expression's own type, and none for an untyped JavaScript value
<tt>fetch(...)</tt>, <tt>encodeURIComponent(...)</tt>, <tt>setTimeout(...)</tt>, <tt>clearTimeout(...)</tt>, <tt>queueMicrotask(...)</tt>: the bare browser functions the DOM table lists as globals, when the class defines no method of that name :: The table's type; <tt>fetch</tt> yields <tt>Promise[Response]</tt>, <tt>setTimeout</tt> an <tt>Integer</tt>
<tt>left + right</tt>, <tt>-</tt>, <tt>*</tt>, <tt>/</tt>, <tt>%</tt> on <tt>Integer</tt> or <tt>Float</tt> operands :: <tt>Float</tt> when either side is, else <tt>Integer</tt>; <tt>String + String</tt> is <tt>String</tt>
A <tt>rescue => name</tt> variable :: <tt>Error</tt>, the DOM table's class for a thrown JavaScript error, so <tt>name.message</tt> reads
<tt>name</tt> or <tt>self.name</tt> for a declared property :: The declared type, including inherited and included declarations
<tt>name(...)</tt> or <tt>self.name(...)</tt> for a collected method :: Its <tt>sig</tt> return type; <tt>void</tt> yields no type
<tt>super(...)</tt> / <tt>super</tt> :: The enclosing method's return type
<tt>receiver.name</tt> where the receiver has a framework class type :: That class's property type or method return type
<tt>receiver.strip</tt> / <tt>upcase</tt> / <tt>downcase</tt> on a <tt>String</tt> receiver :: <tt>String</tt>
<tt>receiver.blank?</tt> / <tt>present?</tt> / <tt>empty?</tt> / <tt>nil?</tt> :: <tt>T::Boolean</tt>
<tt>(expression)</tt> :: The inner expression's type
A member of a DOM-typed receiver :: The DOM table's type for a listed member, the element type for <tt>[]</tt> on a collection, otherwise an untyped JavaScript value
<tt>DOMClass.new(...)</tt> :: That class
<tt>T.must(expression)</tt> :: The expression's type without <tt>T.nilable</tt>; none when the expression is <tt>nil</tt> or untyped
<tt>T.cast(expression, Type)</tt>, <tt>T.let(expression, Type)</tt>, <tt>T.assert_type!(expression, Type)</tt> :: <tt>Type</tt>, as written
<tt>T.unsafe(expression)</tt> :: <tt>T.untyped</tt>, so sends on it are dynamic
<tt>receiver&.member</tt> :: What the member yields, made nilable: the expression is nil when the receiver is

Nilable wrappers are unwrapped where the rule says "class type". Anything not
listed has no static type.

=== Truthiness

Used by <tt>if</tt>, <tt>unless</tt>, ternaries, and unary <tt>!</tt>. Loops are not lowered.

<tt>T::Boolean</tt>, framework class, DOM class, <tt>Array</tt>, <tt>Hash</tt>, <tt>T::Array[...]</tt>, <tt>T::Hash[...]</tt>, nilable class :: The value itself
<tt>NilClass</tt> :: <tt>false</tt>
<tt>String</tt>, <tt>Integer</tt>, <tt>Symbol</tt>, and their nilable forms :: <tt>value != null</tt>
Unknown or <tt>T.untyped</tt> :: <tt>Runtime.isTruthy(value)</tt>

=== Logical operators

Boolean, nil, or native kind (see above) :: <tt>left && right</tt> emits <tt>left && right</tt>; <tt>left || right</tt> emits <tt>left || right</tt>.
Stable scalar (literal or local) :: <tt>left && right</tt> emits <tt>right</tt>; <tt>left || right</tt> emits <tt>left</tt>.
Stable nilable scalar :: <tt>left && right</tt> emits <tt>left != null ? right : left</tt>; <tt>left || right</tt> emits <tt>left != null ? left : right</tt>.
Otherwise :: <tt>left && right</tt> emits <tt>Runtime.logicalAnd(left, () => right)</tt>; <tt>left || right</tt> emits <tt>Runtime.logicalOr(left, () => right)</tt>.

The right operand is deferred in the runtime forms so it evaluates lazily, as
in Ruby. Ruby2JS's own <tt>||</tt> handling is forced to logical <tt>||</tt>; its nullish <tt>??</tt> would
keep a Ruby <tt>false</tt>.

=== Equality

<tt>==</tt> and <tt>!=</tt> compile to <tt>===</tt> / <tt>!==</tt> when either operand has an
identity-comparable type: <tt>String</tt>, <tt>Integer</tt>, <tt>Float</tt>, <tt>Symbol</tt>, <tt>T::Boolean</tt>,
<tt>NilClass</tt>, a nilable form of those, a framework class, or a DOM class. Otherwise they
compile to <tt>Runtime.isEqual(left, right)</tt>, negated for <tt>!=</tt>. Collections such
as <tt>T::Array[String]</tt> are never identity-compared.

=== Receivers

For <tt>receiver.name(args)</tt> where the receiver is not <tt>self</tt>:

Framework class ::
  Declared property, no arguments :: <tt>receiver.name</tt>
  <tt>name = value</tt> for a declared property :: <tt>receiver.name = value</tt>
  Collected method :: <tt>receiver.name(args)</tt>
  Anything else :: Pragma filter if it applies, else an explicit call
  <tt>class</tt> :: <tt>receiver.constructor</tt>
  <tt>receiver&.name</tt> for a declared property :: <tt>Runtime.nilable(receiver?.name)</tt>
  <tt>receiver&.name(args)</tt> for a collected method :: <tt>Runtime.nilable(receiver?.name(args))</tt>
A class object (<tt>T.class_of(Class)</tt>, <tt>self.class</tt>, a class constant) ::
  A static method, or a <tt>ClassMethods</tt> method, registry, or setting :: <tt>receiver.name(args)</tt>, lambdas typed by the signature
A class object ::
  <tt>new(args)</tt> :: <tt>new receiver(args)</tt>
A JavaScript intrinsic or DOM class named as the receiver (<tt>JSON</tt>, <tt>Promise</tt>, <tt>Math</tt>) ::
  Anything but <tt>new</tt> :: Native; <tt>JSON.generate</tt> is <tt>JSON.stringify</tt>
Any ::
  <tt>is_a?(Array)</tt>, <tt>kind_of?(Array)</tt>, <tt>instance_of?(Array)</tt> :: <tt>Array.isArray(receiver)</tt>, so an array from another realm (a page's JSON) counts
  <tt>nil?</tt> :: <tt>receiver == null</tt>
DOM class ::
  <tt>receiver&.name</tt> :: <tt>receiver?.name</tt>, JavaScript's own, since a DOM value is a JavaScript value
Core value type, unknown, or <tt>T.untyped</tt> ::
  <tt>receiver&.name</tt> :: Rejected: these lower through helpers that take the receiver as an argument, which <tt>?.</tt> cannot guard
Core collection ::
  A block of several statements :: The block's last expression is its value, as in Ruby: the body compiles with an explicit return (the converter alone returns only single-expression bodies)
DOM class or untyped JavaScript value ::
  Anything :: Native, per {Native types}[#native-types]
Core value type (below), nilable or not ::
  A method in its table :: The table's form; a method outside the table is rejected
Core value type ::
  Operators, indexing, <tt>new</tt>, or a send with an <tt>array</tt>/<tt>hash</tt>/<tt>string</tt> pragma :: Left to the converter and the Pragma filter, except the array and integer operators the tables name
Any, or implicit self ::
  <tt>respond_to?(:name)</tt> with a literal name :: <tt>Runtime.respondsTo(receiver, "name")</tt>; a dynamic name is rejected
Unknown, <tt>T.untyped</tt>, or <tt>T.proc...</tt> ::
  <tt>call(args)</tt> or <tt>.(args)</tt> :: <tt>receiver(args)</tt> for a local receiver; <tt>receiver.call(null, args)</tt> otherwise
Unknown or <tt>T.untyped</tt> ::
  Operators, indexing, <tt>new</tt>, unary operators, or a send with an <tt>array</tt>/<tt>hash</tt>/<tt>string</tt> pragma :: Left to the converter and the Pragma filter
  No arguments :: <tt>Runtime.read(receiver, "name")</tt>
  <tt>name = value</tt> :: <tt>Runtime.write(receiver, "name", value)</tt>
  Arguments :: <tt>Runtime.invoke(receiver, "name", args)</tt>, resolved against metadata by name and argument count
  Any block :: Rejected: collected methods take no blocks, so only a collection can receive one, and its type must be declared
Any other type ::
  Anything :: Pragma filter if it applies, else an explicit call

No operation is chosen by method name alone. A typed receiver is resolved
statically; an untyped receiver is dynamic, and every send on it is resolved
through installed metadata at run time, as Ruby itself would resolve it. A
model may define its own <tt>strip</tt>: a typed receiver calls it, and an untyped
receiver reaches it through <tt>Runtime.read</tt>, which prefers a collected method
over the string reader. Constants and <tt>self</tt> are never dynamic, and
<tt>Const.new</tt> types its result as that class when the class is collected.

=== Core value types

<tt>filters/core_types.rb</tt> holds one table per Ruby core type. A method in a
table compiles to the JavaScript form where Ruby and JavaScript agree, or to a
<tt>Runtime</tt> helper in <tt>values.mjs</tt> that carries Ruby's rule where they differ.
Each entry also fixes the static type of its result, so chains such as
<tt>name.strip.length > 0</tt> stay typed. A method on one of these receivers that
no table lists is a build error naming the type and method: a gap is
reported, not compiled into a call to a method JavaScript lacks. The tables
grow with real code; <tt>spec/compiler_test.rb</tt> runs one fixture over them on
MRI and as compiled JavaScript and requires identical results.

A <tt>T.nilable(X)</tt> receiver uses <tt>X</tt>'s table. Ruby would raise on nil, and the
JavaScript forms and helpers throw on <tt>null</tt> too, except <tt>to_s</tt>, which is
nil-safe (<tt>Runtime.stringify</tt>) because <tt>nil.to_s</tt> is <tt>""</tt>.

<tt>String</tt> ::

=== Sorbet runtime operations

Executable code may use the <tt>T</tt> methods below; they compile to runtime
checks with sorbet-runtime's behavior, so shared Ruby behaves the same on MRI
and in the browser, and they give the static typer facts. No other <tt>T</tt>
construct is allowed in a body, and no <tt>sorbet-runtime</tt> is bundled.

<tt>T.must(value)</tt> → <tt>Runtime.must(value)</tt> :: Throws <tt>TypeError</tt> for <tt>null</tt> or <tt>undefined</tt>, else returns the value
<tt>T.cast(value, Type)</tt>, <tt>T.let(value, Type)</tt>, <tt>T.assert_type!(value, Type)</tt> → <tt>Runtime.cast(value, "Type")</tt> :: Throws <tt>TypeError</tt> unless the value conforms, else returns it
<tt>T.unsafe(value)</tt> → <tt>value</tt> :: None
<tt>T.absurd(value)</tt> → <tt>Runtime.absurd(value)</tt> :: Always throws <tt>TypeError</tt>

A checkable <tt>Type</tt> is a declaration type, <tt>Float</tt>, <tt>Symbol</tt>, <tt>NilClass</tt>, or
<tt>T.untyped</tt>. A class name is resolved in Ruby scope and emitted as the name the
class is installed under, so the check is <tt>instanceof</tt> against the installed
class. A DOM class or intrinsic is accepted, and a cast to one, or to
<tt>T.untyped</tt>, is an annotation only, with no runtime check. <tt>T::Array[...]</tt> and <tt>T::Hash[...]</tt> check the container only,
not its elements, as sorbet-runtime does. Unions, procs, mixins, and unknown
constants are rejected. <tt>T.let</tt> on an assignment keeps its check and types the
local; the upstream Pragma filter would otherwise erase it.

=== Asynchrony

<tt>async</tt> and <tt>await</tt> are reserved forms with JavaScript's meaning. `async def
name<tt> (Ruby parses it as </tt>async(def ...)`) declares an asynchronous method,
compiled with the <tt>async</tt> keyword, so calling it yields a promise. `await
expression<tt> inside such a method compiles to </tt>await<tt>. </tt>await` outside an
async method, or inside a block or lambda within one (their functions are
not the method), is rejected. On MRI, <tt>Swill::Object</tt> provides <tt>async</tt> as a
no-op wrapper and <tt>await</tt> as the identity, so shared code runs synchronously
there.

An async method's signature names the value it yields, not the promise:
<tt>sig { returns(T.attached_class) }</tt> on <tt>async def self.find(id)</tt> means `await
Menu.find(id)<tt> is a </tt>Menu<tt> to the compiler and, through </tt>await`'s generic
identity signature, to Sorbet. A call without <tt>await</tt> is a <tt>Promise</tt>. The
DOM table writes <tt>Promise[Response]</tt> for <tt>fetch</tt>; the RBI shows Sorbet the
element, as MRI's <tt>await</tt> would yield it, and the compiler types the awaited
value. <tt>Promise.all</tt>, <tt>Promise.resolve</tt>, and the rest of the browser's
promise API are native, as any DOM class is, and their awaited values are
untyped.

=== Exceptions

<tt>raise "message"</tt> and <tt>raise "interpolated #{message}"</tt> compile to
<tt>throw new Error(...)</tt>. Bare <tt>raise</tt>, <tt>raise SomeClass</tt>, <tt>raise SomeClass, msg</tt>,
and <tt>raise variable</tt> are rejected. <tt>begin</tt>/<tt>rescue => error</tt>/<tt>ensure</tt> is the
converter's <tt>try</tt>/<tt>catch</tt>/<tt>finally</tt>; the rescued variable is typed <tt>Error</tt>,
so <tt>error.message</tt> is a native read. Rescuing a named class is outside the
boundary: a thrown value is whatever JavaScript threw.

=== Safe navigation

<tt>receiver&.member</tt> is lowered wherever the compiler resolves the member
statically: a declared property reads, a collected method is called, and each
hop guards the next, so <tt>recipe&.detail&.glassware</tt> is one expression. A core
value type and an untyped receiver are rejected, because both lower through
helpers that take the receiver as an argument, and <tt>?.</tt> cannot guard an
argument.

Two things about the output are deliberate. The result passes through
<tt>Runtime.nilable</tt>, because JavaScript's optional chaining answers <tt>undefined</tt>
where Ruby answers <tt>nil</tt>, and <tt>undefined</tt> is a second spelling of nothing that
would leak to application JavaScript and disappear from <tt>JSON.stringify</tt>. A
chain normalizes once, at the end. And a DOM receiver keeps plain <tt>?.</tt>
without that wrapper: those are JavaScript values, which the compiler already
types as such.

== Runtime reference

<tt>rb/runtime/runtime.mjs</tt> exports one object, <tt>Runtime</tt>. It holds browser state
and installs metadata. It never interprets Ruby source or ASTs, never patches
prototypes it did not create, and provides no universal dynamic send.

=== Installation

<tt>install(meta)</tt> :: Validates every entry first, then installs classes superclass-first regardless of key order. Errors: <tt>Duplicate class</tt>, <tt>Missing constructor</tt>, <tt>Unknown mixin for</tt>, <tt>Duplicate constructor in meta</tt>, <tt>Mixin factory must be a function</tt>, <tt>ClassMethods factory must be a function</tt>, <tt>Unresolvable superclass order in meta</tt>
<tt>include(klass, mixins, incoming)</tt> :: Rewires <tt>klass</tt> and <tt>klass.prototype</tt> through the mixin layers once, before instances exist, and copies <tt>ClassMethods</tt> helpers onto the constructor. Error: <tt>Mixins must be attached before class installation</tt>
<tt>installClass(klass, name, properties, methods, registries, restorations, settings)</tt> :: Records metadata, applies settings and exact registry snapshots, defines accessors on the prototype, and registers the name. Errors: <tt>Duplicate class</tt>, <tt>Setter method for declared property</tt>, <tt>Restorable path must start with a declared property</tt>, <tt>Duplicate restorable key</tt>, <tt>Missing registry declaration</tt>, <tt>Missing setting declaration</tt>
<tt>resolve(name)</tt> :: Returns the registered constructor for a Ruby name. Fails closed with <tt>Unknown class</tt>; markup cannot reach globals or prototypes

Metadata is inherited: a class's property and method tables start from its
parent's, so lookups do not walk the chain at call time.

Conflicts with installed metadata are rejected here, not by the compiler:
the compiler rejects what it cannot compile or emit, and the runtime rejects
metadata it cannot install or honor. A <tt>name=</tt> method for a declared or
inherited property would be replaced or bypassed by the installed accessor;
mutation belongs in <tt>name_did_change</tt>. A <tt>restorable</tt> path must start at a
declared property for the path writer to reach it, and fragment keys must be
unique along the class chain. Checking at installation also covers classes
registered from JavaScript, which the compiler never sees.

=== Metadata-driven dispatch

<tt>read(object, name)</tt> :: On a null receiver, <tt>nil?</tt>, <tt>blank?</tt>, <tt>present?</tt>, <tt>to_s</tt>, <tt>to_i</tt>, and <tt>to_f</tt> answer for nil and every other name yields <tt>null</tt>. Primitives go straight to <tt>valueRead</tt>. A plain object is a Hash: its entry by key, <tt>null</tt> when absent, then the value readers, as key-value coding treats a dictionary; entries are not observable. Otherwise a declared property, then a collected method that takes no arguments, then <tt>valueRead</tt> for the value reader names. Error: <tt>Unknown reader</tt>
<tt>write(object, name, value)</tt> :: A declared stored property through the property protocol, or a collected <tt>name=</tt> accessor. A plain object is a Hash: an entry it already has is set, as key-value coding does for a dictionary. Errors: <tt>Cannot write ... on nil</tt>, <tt>Read-only property</tt>, <tt>Unknown writer</tt>, <tt>Unknown key</tt>
<tt>readPath(object, "a.b.c")</tt> :: Folds <tt>read</tt> over the segments; a null intermediate yields <tt>null</tt>; the empty path is the object itself
<tt>writePath(object, path, value)</tt> / <tt>assertWritablePath(object, path)</tt> :: Resolves the owner with <tt>read</tt> and requires a stored property, or an existing key of a Hash owner, at the end. A missing intermediate owner makes the write a no-op, since the owner may appear later. Errors: <tt>Read-only binding</tt> when the leaf is computed, not a property, or the path is empty; <tt>Unknown key</tt> for a Hash owner without the key
<tt>invoke(object, name, ...args)</tt> :: Calls the member of the named method's family whose arity is the argument count; the dynamic call compiled for an untyped receiver. Errors: <tt>Cannot call ... on nil</tt>, <tt>Unknown method or wrong arity</tt>
<tt>respondsTo(object, name)</tt> :: Ruby <tt>respond_to?</tt> over metadata: a declared property, its writer when stored, a collected method, or a value reader on nil and plain values. The JavaScript object shape is never consulted. The responder chain uses it to decide which responder handles an action
<tt>outlets(object)</tt> :: The property descriptors declared with <tt>outlet</tt>, including inherited ones; awakening connects them
<tt>restorations(object)</tt> :: The <tt>restorable</tt> declarations, including inherited ones, as <tt>{path, key, type}</tt>
<tt>decodeFragment(type, text)</tt> / <tt>encodeFragment(value)</tt> :: Fragment values are strings; a declared <tt>Integer</tt> or <tt>T::Boolean</tt> leaf decodes, anything else stays text, and an undecodable value is <tt>undefined</tt>. Encoding maps nil and <tt>""</tt> to removal
<tt>warn(message)</tt> :: The one console boundary, for wrong untrusted URL input
<tt>isAttribute(object, name)</tt> :: Whether <tt>name</tt> is a declared <tt>attribute</tt> on the object's class
<tt>validateAttribute(object, name, value, previous)</tt> :: Runs a collected <tt>validate_<name>(value, previous)</tt> method for a declared attribute, else returns the value. A <tt>validate_<name></tt> that cannot take both throws rather than silently never running. The MRI host implements the same convention with <tt>respond_to?</tt>
<tt>performAction(object, name, sender, event)</tt> :: Calls the widest member of the named method's family that takes at most two arguments, with <tt>sender</tt> and <tt>event</tt> sliced to fit. Same error
<tt>nameOf(object)</tt> :: The installed name of the object's nearest installed class, or <tt>null</tt>
<tt>valueRead(value, name)</tt> / <tt>valueInvoke(value, name, args)</tt> :: Ruby's core methods on plain values, reached by <tt>read</tt> and <tt>invoke</tt> when the receiver has no declared member of that name: the predicates, <tt>size</tt>, <tt>length</tt>, <tt>strip</tt>, <tt>upcase</tt>, <tt>downcase</tt>, <tt>capitalize</tt>, <tt>dup</tt>, <tt>first</tt>, <tt>last</tt>, <tt>compact</tt>, <tt>uniq</tt>, <tt>reverse</tt>, <tt>sum</tt>, <tt>min</tt>, <tt>max</tt>, <tt>to_s</tt>, <tt>to_sym</tt>, <tt>to_i</tt>, <tt>to_f</tt>, and with arguments <tt>index</tt>, <tt>take</tt>, <tt>drop</tt>, <tt>include?</tt>. <tt>dup</tt> copies an array or hash; on an object with declared properties, <tt>read</tt> answers <tt>dup</tt> with a new instance carrying the stored properties, written through the property protocol; array methods refuse other values. Errors: <tt>Unknown value reader</tt>, <tt>Unknown value method</tt>

=== Values

<tt>isTruthy(value)</tt> :: Ruby truthiness: everything except <tt>false</tt>, <tt>null</tt>, and <tt>undefined</tt>
<tt>logicalAnd(left, thunk)</tt> / <tt>logicalOr(left, thunk)</tt> :: Ruby <tt>&&</tt> / <tt>||</tt> with a deferred right operand
<tt>isEqual(left, right)</tt> :: <tt>===</tt>, or element-wise for two arrays. Hashes and custom <tt>==</tt> are not implemented; framework objects compare by identity
<tt>isBlank(value)</tt> :: <tt>null</tt>, <tt>undefined</tt>, <tt>false</tt>, a string that strips to empty, or an empty array
<tt>isPresent(value)</tt> :: The negation of <tt>isBlank</tt>
<tt>isEmpty(value)</tt> :: Zero length for a string or array; anything else throws <tt>TypeError</tt>
<tt>strip(value)</tt> :: Removes ASCII whitespace and NUL from both ends, as Ruby does; JavaScript <tt>trim</tt> would also remove NBSP. Non-strings throw <tt>TypeError</tt>
<tt>upcase(value)</tt> / <tt>downcase(value)</tt> :: <tt>toUpperCase</tt> / <tt>toLowerCase</tt>; non-strings throw <tt>TypeError</tt>
<tt>length</tt>, <tt>stringify</tt>, <tt>toInteger</tt>, <tt>toFloat</tt>, <tt>capitalize</tt>, <tt>split</tt>, <tt>slice</tt>, <tt>sort</tt>, <tt>sortBy</tt>, <tt>minBy</tt>, <tt>maxBy</tt>, <tt>min</tt>, <tt>max</tt>, <tt>sum</tt>, <tt>uniq</tt>, <tt>compact</tt>, <tt>flatten</tt>, <tt>reverse</tt>, <tt>indexOf</tt>, <tt>append</tt>, <tt>prepend</tt>, <tt>difference</tt>, <tt>fetch</tt>, <tt>deleteKey</tt>, <tt>intDiv</tt>, <tt>modulo</tt>, <tt>between</tt>, <tt>clamp</tt> :: Core type methods whose Ruby rule differs from JavaScript's; the core value types section lists which method each serves. <tt>isBlank</tt>, <tt>isEmpty</tt>, and <tt>length</tt> also accept a plain object as a Hash

=== Sorbet runtime operations

<tt>must(value)</tt> :: Returns the value; throws <tt>TypeError</tt> for <tt>null</tt> or <tt>undefined</tt>
<tt>cast(value, type)</tt> :: Returns the value when it conforms to the type text (a declaration type, <tt>Float</tt>, <tt>Symbol</tt>, <tt>NilClass</tt>, <tt>T.untyped</tt>, or an installed class name); otherwise throws <tt>TypeError</tt>. Containers are checked shallowly
<tt>absurd(value)</tt> :: Throws <tt>TypeError</tt>
<tt>conforms(value, type)</tt> :: The check behind <tt>cast</tt>, as a boolean; awakening uses it for typed outlets

=== Observation

<tt>observe(object, name, callback)</tt> :: Subscribes to a declared property; the callback receives <tt>(value, previous)</tt>. Observing a computed property computes it first so its dependencies exist. Returns a disposer. <tt>Swill::Observable#observe</tt> retains it on the observer, so framework plumbing whose disposer belongs to something else — a wired region, a list row — calls this primitive instead. Error: <tt>Unknown observable property</tt>
<tt>observePath(object, path, callback)</tt> :: Subscribes along every observable segment, rehooks the subtree before invoking the callback when an intermediate changes, and passes the new path value. Returns a disposer that also stops any in-flight rehook
<tt>retain(object, disposer)</tt> :: The object claims the disposer and is responsible for letting it go, as Cocoa's retain claims an object. Answers the disposer
<tt>release(object, disposer)</tt> :: Gives up a claim before the object goes away, ending the disposer. One never retained still ends
<tt>dealloc(object)</tt> :: End of life: releases everything the object retained, then disconnects it. Draining first means nothing an observer does can re-enter
<tt>disconnect(object)</tt> :: Releases computed dependency subscriptions and observers, invalidates outside computed values that depended on the object, and keeps stored values. A later or eagerly observed read builds a fresh dependency graph

=== Attributes and class configuration

<tt>collectAttributes(object, only = null)</tt> :: <tt>{key: value}</tt> for every stored <tt>attribute</tt> declaration, including inherited ones; with an array of names, only those
<tt>identityStore(klass)</tt> :: The class's own <tt>Swill::Model::Store</tt>, created on first use
<tt>classWithSetting(name, value)</tt> :: The installed class whose own setting, by Ruby name, has the value, or <tt>null</tt>: how a JSON:API type finds its model class
<tt>applyAttributes(object, source)</tt> :: Assigns each attribute from <tt>source[key]</tt>, else <tt>source[name]</tt>, through the property protocol
<tt>Model::Attributes.from_attributes(source)</tt> :: Class method from the shared mixin: <tt>new</tt> plus <tt>apply_attributes</tt>, so <tt>decode_outlet_data</tt> can hand an outlet typed <tt>T::Array[Person]</tt> real people
<tt>inheritableRegistry(klass, name, "hash" | "array")</tt> :: Returns the class's own registry, created on first access as a copy of the parent's
<tt>classSetting(klass, name, values)</tt> :: With one value, stores it; with none, returns the class's own value or the parent's; more than one value throws. <tt>installClass</tt> applies a class body's <tt>settings</tt> through the setting method after mixins are attached, and throws for a setting no <tt>ClassMethods</tt> declares

== Property protocol

Accessors installed by <tt>installClass</tt> share one mutation path, and one read
path:

  write: read previous → coerce_property_value(name, value, previous)
    → compare with isEqual → property_will_change(name, previous, value)
    → store → notify

  read: record the dependency → property_will_access(name) → resolve

The three hooks are Cocoa's, and a class overrides them rather than redefining
an accessor:

<tt>coerce_property_value(name, value, previous)</tt> :: Before a write. Cocoa's <tt>-validateValue:forKey:error:</tt>.
<tt>property_will_change(name, previous, value)</tt> :: Before a write lands. Cocoa's <tt>-willChangeValueForKey:</tt>.
<tt>property_will_access(name)</tt> :: Before a read returns. Cocoa's <tt>-willAccessValueForKey:</tt>.

<tt>property_will_access</tt> runs only for a property declared <tt>will_access:</tt>, so an
ordinary read costs nothing. <tt>Swill::Model::Base</tt> overrides it to load a
relationship nobody prefetched: reading <tt>recipe.ingredients</tt> answers what it
has and fills in when the request lands. The guard — the record has an id and
<tt>ingredients_loaded</tt>, <tt>ingredients_loading</tt>, and <tt>ingredients_error</tt> are all
clear — is what keeps a re-render from re-requesting; <tt>reload_<name></tt> is how an
application asks again. Reads and explicit callers share the same in-flight
request.

Those four properties are the whole of a relationship's key-value loading
state, in AVFoundation's sense, and every one of them is observable. A spinner,
an empty state, and a failure are bindings. An explicit <tt>load_<name></tt> or
<tt>reload_<name></tt> rejects after recording the error, so a caller that chose to
await it handles the failure normally. The automatic load started by a read
catches and warns after recording the same error:

  property :menu_recipes, type: T::Array[MenuRecipe] do
    menu = selected_menu
    menu ? menu.recipes : []
  end

Reading <tt>menu.recipes</tt> inside the computed both registers the dependency and
starts the request, so selecting a menu fills the list and nothing calls a
loader.

<tt>notify</tt> runs, in order: dependents of the property (computed invalidation),
the <tt>name_did_change(previous, value)</tt> method if the class collected one, then
public observers. Dependents run first so a hook that reads a derived property
sees a fresh value.

Computed properties record every <tt>(object, property)</tt> read during <tt>compute</tt>
through a capture stack. Each recompute replaces the previous dependency
subscriptions, so a branch that stops reading an object stops observing it.
Invalidation drops the cache and recomputes eagerly only for something that
must learn of the change: an observer, or the property's own
<tt>name_did_change</tt> hook. A computed property whose class defines that hook is
therefore evaluated when the object's state is first touched, so the hook
runs on every dependency change with the previous and new values, as
<tt>Swill::Controller::List</tt> relies on for <tt>selected_object_did_change</tt>; a
computed property without a hook stays lazy until read or observed. Cycles
throw <tt>Computed cycle</tt>; an exception inside <tt>compute</tt> unwinds the capture
stack.

Per-object state lives in a <tt>WeakMap</tt>, so objects need no reserved fields and
are collected normally. Drafts copy attributes through <tt>apply_attributes</tt> and
therefore carry no subscriptions or computed state.

== Rejected forms

Every rejection is a <tt>Swill::Ruby2JS::CompileError</tt> at build time. Grouped by
where it is raised:

Top level :: Anything other than <tt>class</tt> and <tt>module</tt>
Constants :: Unknown or non-static constants; reopened or duplicate constants; a superclass or mixin defined later in the same build; a superclass that is a mixin; an include target that is a class
Methods :: Names outside <tt>/\A[a-z_]\w*[!?=]?\z/</tt>; <tt>method_missing</tt>; optional, keyword, splat, or block parameters; a method whose name is also an inherited property
Declarations :: A macro's own keywords are Ruby's, so a missing or unknown one is rejected where it is written. The declaration primitives reject: an unsupported property name, a stored property ending in <tt>?</tt>, a duplicate name, a mutable default, a computed property with a default, a computed outlet, a restorable path that is not dotted property names, and registry storage other than <tt>:hash</tt> or <tt>:array</tt>. The compiler rejects a declared class name that does not name a class, and a class body that calls something no ancestor declares. Which classes may declare <tt>outlet</tt> and <tt>restorable</tt> is where their macros are defined; whether a <tt>restorable</tt> path starts at a declared property, and whether keys collide, is checked by the runtime at installation
Mixins :: Properties or includes on a mixin itself; a second <tt>self.included</tt>; non-literal hook bodies; <tt>base.extend</tt> of anything but <tt>ClassMethods</tt>; declaring <tt>ClassMethods</tt> without contents; the same mixin included twice along one ancestor chain; <tt>prepend</tt>
<tt>ClassMethods</tt> :: Non-literal registry or setting names; registry storage other than <tt>:hash</tt> / <tt>:array</tt>; <tt>class_setting</tt> coercion blocks; any other statement
Expressions :: Any <tt>T</tt> construct in an executable body other than <tt>T.must</tt>, <tt>T.cast</tt>, <tt>T.let</tt>, <tt>T.assert_type!</tt>, <tt>T.unsafe</tt>, and <tt>T.absurd</tt> with the right number of arguments; a type argument outside the checkable types, or naming a mixin or an unknown constant; <tt>public_send</tt>, <tt>send</tt>, <tt>__send__</tt>, <tt>const_get</tt>, <tt>define_method</tt>, <tt>instance_exec</tt>, <tt>eval</tt>; <tt>respond_to?</tt> with a non-literal name; a block on an untyped receiver; a method or block on a core value type receiver outside its lowering table, or with the wrong number of arguments; safe navigation (<tt>&.</tt>) on the shared surface
Exceptions :: Any <tt>raise</tt> form other than a literal message string
Pragmas :: Any pragma other than <tt>array</tt>, <tt>hash</tt>, <tt>string</tt>
Members :: Two members with the same encoded JavaScript name
Build :: Application compilation without a framework import; missing <tt>esbuild</tt>; unformattable output

Ruby that reaches Ruby2JS unlowered and that Ruby2JS cannot convert also fails
the build with Ruby2JS's own error.

=== Disabled upstream filters

Functions :: Rewrites ordinary framework methods without type evidence
ActiveSupport :: Its <tt>blank?</tt> behavior conflicts with Swill value readers
ESM / Require :: Imports and exports come from compiler metadata
camelCase / underscore :: Source names and metadata keys must remain stable

== Extending the boundary

The supported subset is defined by accepted source and behavioral tests, not
by whatever JavaScript Ruby2JS can emit. For each new construct, in order:

1. Use Ruby2JS unchanged when its output preserves the required semantics.
2. Use an upstream filter only when its relevant behavior matches Swill's
   truthiness, naming, metadata, and packaging rules.
3. Add a Swill filter for syntax, static type-directed operations,
   declaration-aware access, or compile-time rejection.
4. Add runtime support only for execution-time types, shared state, identity,
   or an application-wide protocol.
5. Otherwise reject the construct explicitly.

Filters may lower syntax and choose operations from static knowledge. They must
not hold application state or create a second framework protocol. Runtime
helpers implement genuinely dynamic or shared behavior and must not interpret
Ruby source. A universal dynamic call helper is intentionally excluded; it
would hide the supported surface and grow into a second Ruby VM.

Rules must cover a coherent class of values, not one fixture. Every addition
should include:

* a production-shaped motivating expression;
* MRI comparison for shared Ruby code (<tt>spec/shared_test.rb</tt>);
* relevant Ruby/JavaScript edge values;
* generated-code assertions when placement matters (<tt>spec/compiler_test.rb</tt>);
* executable runtime coverage (<tt>spec/runtime_test.mjs</tt>);
* rejection of the nearest unsupported form;
* verification that application bundles do not duplicate the runtime
  (<tt>spec/bundle_test.mjs</tt>);
* an update to this document when the boundary moves.
